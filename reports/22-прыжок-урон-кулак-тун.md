# 22. Прыжок, урон по клону, кулак и предложение селлшейдинга

Дата: 17 ноября 2026. Четыре бага из живого запуска плюс вопрос о стиле.

## 1. Прыжок не работал — и физически не мог

Это не «кнопка не та» и не «буфер сломан». Прыжок **гасился через одну
строку после запуска**. Порядок операций был такой:

```
1. _try_jump()          -> velocity.y = +7.43   (скорость для высоты 1.15 м)
2. if not is_on_floor() -> ложь: персонаж ещё на полу
   elif _action != "dodge": velocity.y = 0.0    <- вот здесь прыжок и умирал
3. move_and_slide()     -> уже с нулевой вертикальной скоростью
```

То есть в том же кадре, где прыжок начинался, «прилипание к полу»
обнуляло скорость взлёта. Персонаж не отрывался ни на миллиметр.

Исправлено: гашение вертикальной скорости выполняется **до** прыжка и
только когда персонаж падает (`velocity.y <= 0.0`), а не всегда.

## 2. Хп клона не отнималось — список целей был пуст

Также не «урон не проходит»: удар **не по кому было считать**.

Список целей набирался **один раз** в `_ready()` героини. Но порядок
добавления в сцену такой, что героиня оказывается в дереве раньше клона:
на момент её `_ready()` в группе `damageable` ещё никого нет. Список
оставался пустым на весь бой.

Исправлено: список пополняется перед каждым ударом (`_refresh_targets`).
Заодно удар теперь выбирает **ближайшую** цель в конусе, а не первую
попавшуюся в списке — иначе при двух противниках он уходил бы в дальнего.

В отладочную строку добавлена причина: вместо «цель: —» теперь видно
`мимо (до цели 2.4 м)`, если удар не достал. Так сразу понятно, промах
это или дыра в коде.

## 3. «Бьют тыльной стороной ладони» — две отдельные причины

### 3.1 Неверная ориентация кисти

Расчёт по осям покоя показал: в позе удара нормаль ладони смотрела
в наружу-вверх (`X −0.92, Y +0.12`), то есть вперёд шла именно тыльная
сторона кисти. Наружу смотрели и пальцы.

Перебором 3000 комбинаций (скрутка плеча, скрутка предплечья, скрутка
кисти по двум осям) найдено решение: **скрутка вдоль оси кости** —
плечо 40°, предплечье 60°. Ладонь разворачивается вниз: отклонение
нормали от «вниз» 4° вместо 97°.

Тонкость, на которой я сначала ошибся: **знак скрутки у обеих рук
одинаковый**, хотя отведение в сторону (Z) зеркальное. При зеркальном
знаке правая рука давала 159° (тыльная сторона вперёд — ровно жалоба),
левая 21°. Причина — кость правой руки в позе покоя развёрнута на 180°
относительно левой.

### 3.2 Пальцы были раскрыты — в скелете нет костей пальцев

Даже с правильной ориентацией удар не выглядел ударом: кисть
раскрыта, пальцами не пошевелить. В скелете всего **21 кость**, и
последняя — кисть.

Но в исходной модели есть готовый морф **`Fists`** и три промежуточных
сжатия. Он двигает ровно кисти: 3400 вершин, все принадлежат `hand.L` /
`hand.R` (1700 + 1700), максимальный сдвиг 98 мм, выше кистей ничего
не задето.

Морфы — это то, на чём падал редактор Godot, тащить их обратно нельзя.
Поэтому в `sanitize_glb.py` добавлена `bake_fists_into_geometry`: смещения
морфа `POSITION` и `NORMAL` прибавляются к базовой геометрии, нормали
перенормируются, морфы выкидываются.

Кулак стал постоянным. Для soulslike это нормально: рука всё равно сжата
(а «сжатый кулак» и раньше упоминался в README модели как нужная поза).

| | размах кисти X | размах Z |
| --- | --- | --- |
| раскрытая ладонь | 0.052 | 0.103 |
| **кулак** | **0.066** | **0.080** |

Порядок операций в скрипте важен: кулак впечатывается **до** `strip()`
(иначе морфов уже нет) и **до** сшивки швов (сшивка усредняет веса,
геометрию не трогает). Швы после сшивки — 0.0000 мм в ударах обеими руками.

## 4. Стойка переделана под кулак

С кулаком прежняя стойка (локоть 125°) выглядела как «кулаки у носа».
Подобрано перебором: плечо 20–24°, локоть 140°. Кисть выходит на
Y 1.29 (уровень подбородка), X −0.17, Z +0.24, локоть опущен на Y 1.10.

Ошибка, которую поймал по пути: при локте 45° кулак висел на уровне
пояса (Y 0.91). Проверять надо не «углы похожи на боевые», а **где
оказалась кисть**.

## 5. Селлшейдинг — да, и это правильный вывод

Пользователь: «мы можем сделать селлшейдинг? мне кажется он будет лучше,
потому что нормальное обычное освещение мы сюда вряд ли завезём».

Согласен, и вот почему это не «костыль, потому что не умеем», а верное
решение для этой модели:

| Факт | Следствие |
| --- | --- |
| кожа — почти ровная заливка (яркость 0.77, стд 0.09) | плавному затенению нечего показывать |
| нормал-карт нет | микрорельефа нет вообще |
| материал модели: `doubleSided`, roughness 0.88 | блики ничего не дают |
| один скин-меш, 33 300 треугольников | геометрия гладкая, без складок одежды |

У PBR на такой модели **нет входных данных** для объёма: он рисует
плавный градиент по гладкой поверхности — отсюда и «посасывает», сколько
ни подбирай лампы. Toon работает наоборот: он рисует **ступени**, и объём
создают сами границы ступеней. Плюс контровой контур по краю силуэта —
без него белая модель на белой стене сливается.

Сделано: шейдер `TOON_SHADER` в `scripts/build_scene.gd`, применяется в
`main.gd` после спавна. Ступени: тень 0.30 → полутень 0.62 → свет 0.88 →
1.0, границы мягкие (`softness 0.02`), контровой свет по краю.

**Переключатель `TOON_ENABLED` в `tuning.gd`** — специально, чтобы можно
было сравнить два стиля на экране, а не выбирать вслепую.

Глаза и линию века шейдер не трогает: у них своя текстура, и они должны
оставаться тёмными, иначе взгляд пропадает.
